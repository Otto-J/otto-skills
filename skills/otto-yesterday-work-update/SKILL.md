# Otto Yesterday Work Update

生成一份能直接用于晨会的中文工作交接，按仓库说明昨天完成了什么、还剩什么和今天要跟进什么。

## 仓库范围

- 默认只检查当前 Git 仓库。
- 用户明确提供的 Git 路径或仓库名称一律纳入。
- 用户说“全部工作仓库”“所有仓库”或“所有 Git”时，读取 [默认仓库清单](references/repositories.md)，只处理其中列出的仓库。
- 不扫描整个 Home 目录，也不根据目录名猜测仓库；找不到或不是 Git 仓库的路径应在报告中标明，不能静默忽略。
- 用户说“把某仓库加入默认范围”时，先核对其 Git 根目录，再更新默认仓库清单；除此以外不修改清单。

## 取证

1. 按用户本地时区确定窗口；未指定时，“昨天”按 Asia/Shanghai 的自然日计算，并在报告里写出绝对日期。
2. 对每个纳入的仓库读取 `git status --short --branch`、该窗口内当前用户的提交，以及仓库可用时的 PR 记录。优先从该仓库的 `git config user.name` 和 email 确定作者。
3. 需要判断远端合并或 PR 状态时，再执行 `git fetch --all --prune` 和 `gh pr` 查询。认证、网络或权限失败时，明确报告未验证的边界；不得把本地提交当作已合并 PR。
4. 同一提交或 squash merge 的等价变更只计一次。按仓库和产品结果归组，不输出原始提交列表，除非用户明确要求。
5. 这是只读汇总。只有用户明确要求“该合并的做合并”时，才逐个检查 open PR 的 review、checks、mergeable 状态并执行合并；普通晨会请求绝不改分支、提交、推送或合并。

## 报告格式

默认用下面的结构；多仓库时，每段内按仓库标注：

```text
昨天（YYYY-MM-DD）主要完成了……

还没完成的是……

今天需要跟进……

证据边界：……
```

完成项描述用户得到的结果，而非提交标题；未完成项必须带具体状态或阻塞原因。若工作树 dirty、处于 detached HEAD，或 PR 结论无法独立验证，放进“证据边界”。

## 常用调用

- “更新我昨天的工作”——仅当前仓库。
- “汇总我昨天在全部工作仓库的工作”——使用默认仓库清单。
- “把 `/path/to/repo` 也纳入昨天工作更新”——当前仓库加该路径。
- “将 X 加入默认工作仓库”——核对后更新清单。
