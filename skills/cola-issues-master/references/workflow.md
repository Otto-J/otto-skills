# Issue-to-PR 工作流

这个工作流控制一次 Cola Issue 修复的证据顺序、变更边界和完成标准。根据问题类型裁剪步骤，但不能跳过根因门槛、修改前 baseline、验证结论或授权边界。

## 1. Intake：先还原用户问题

### 读取上下文

- 接受一个明确的 `marswaveai/cola` Issue URL 或编号，不自行挑选其他 Issue。
- 用 `collect-issue-context.mjs` 获取经过脱敏的原始 Issue body 和全部 comments。
- 完整读完后先写一句第一人称用户故事：操作、预期、实际现象、受阻结果。
- Comments 只作为已有调查、关联 PR 和待验证假设。不要因为评论看起来完整就跳过独立检查。
- 如果用户问“是否已经修复”，分别验证当前 checkout、远端 PR/commit、main 和 released build；不要把其中一个状态代替另一个。

### 建立证据账本

维护四组简短记录：

- **事实**：截图、日志、trace、数据库、可重复实验或当前代码直接证明。
- **推断**：能够解释事实，但还没有确定性回放。
- **缺口**：缺少的附件、时间、原始输入、账号态或平台条件。
- **排除项**：同一时间出现但无法解释本操作和现象的错误。

不要把原始 signed URL、邮箱、用户/设备 ID、token、提示词或完整会话内容带入回复、提交、PR 或经验库。

## 2. Route：按用户可见对象选择证据

先识别“究竟哪个对象坏了”，再选择工具。

### 视觉、预览或生成产物

证据优先级：

1. 查看截图或录屏中的可见特征、文件名、模式和界面位置。
2. 按 artifact basename 搜索 trace/session 中的生成、写入或编辑动作。
3. 只提取安全结构事实，例如字节数、扩展名、是否有 wrapper/charset、生成时间；不要回显完整正文。
4. 检查文件从磁盘到 protocol、store、renderer/WebView 的数据流。
5. 建立能表现同一可见故障的最小 fixture。

视觉问题通常没有异常。除非 ERROR 与同一操作、时间、组件或 correlation ID 对齐，否则不要因为日志里恰好有 ERROR 就扩展到 Sentry。

### 状态、流式、重复、闪烁或会话问题

- 比较底层数据是重复产生还是同一数据被重复投影、mount 或动画。
- 用事件、持久化记录和 UI projection 还原最小状态转换。
- 一次同时发生的 reconnect、timeout 或 warning 只有能解释该转换时才相关。

### 启动、崩溃、网络或外部服务

- 从用户操作前一个有意义状态开始排序日志。
- 区分首次警告与后续 readiness/恢复证据。
- 外部服务问题按 request/correlation ID、时间、release、环境和操作联合匹配。

### 额度、计费或模型选择

- 按用户消息逐轮连接 session/model/cache 变化、累计模型处理量和账单记录。
- 没有 cloud ledger 时，不从本地 token 或 UI 计数推断实际扣费。

## 3. Root-cause gate：先证明，再修

开始修改前必须能回答：

1. 用户可见的哪个对象或动作具体出错？
2. 正常流程与实际流程在哪里第一次分叉？
3. 候选原因能否通过最小状态或输入重现相同可见效果？
4. 是否存在更靠前、能够同时解释全部现象的边界？

根因分级：

- **Confirmed**：用户运行证据或确定性本地回放把触发条件连接到可见结果。
- **Likely**：代码路径和现象吻合，但缺少关键输入或回放。
- **Unconfirmed**：只有时间巧合、相似错误或评论推测。

历史 Issue、已有 PR 和经验库可以缩短候选路径，但不能替当前 Issue 完成确认。机制已确认而用户特定输入缺失时，明确写成“机制 Confirmed、当前触发 Likely”。

只在 Confirmed，或用户知情同意的高价值 Likely 实验下修改代码。

## 4. Baseline：修改前留证

- 在外部临时目录或 `cola-cdp-test/runs/` 创建最小 fixture，不把调试素材放进产品仓库。
- 在未修改代码上执行一次，记录可断言的失败状态：DOM、协议字段、状态机输出、错误代码或用户可见文本。
- 如果无法本地复现，说明用户附件能证明什么、不能证明什么；不要把修改后的成功当成修改前一定失败的证明。
- 设计 fixture 时只保留触发问题的最小条件，避免把用户私人内容复制进去。

## 5. Repair：修第一处分叉

- 先检查 `git status`、基线和适用的 `AGENTS.md`。
- 保留用户已有改动；只暂存本次文件，禁止宽泛 `git add .` 或 `git add -A`。
- 选择能恢复正确数据契约的最小修改，而不是在下游吞错、重试或替换显示。
- 修改规模超过项目约定时先拆分提交或 PR。
- 生产代码遵循 async I/O、native module 懒加载、TypeScript 和 UI/i18n 约定。
- 若根因在外部依赖或 cloud 服务，修复应落在真正拥有失败边界的仓库，不向 Cola 塞 workaround。

## 6. Verify：分层验证

### 行为测试

- 测输入 → 输出或可观察副作用，不断言内部实现细节。
- 同时覆盖本次失败输入和一个不应受影响的相邻输入。
- 测试必须能在回退修复后失败；只匹配新增文案或函数存在不算回归测试。

### 静态检查

- 运行受影响 package 的测试、typecheck、lint/format 和 `git diff --check`。
- 明确记录命令与结果；依赖缺失、命令未运行和测试失败是三种不同状态。

### 真实运行时

- 使用隔离的 Cola profile，按项目约定从 `npm run dev:cola2` 启动。
- 先确认实际启动命令能找到 binary、调试参数确实传入，并快速检测端口；不要等长超时才发现启动器参数被吞。
- 自动脚本直接断言关键状态并在失败时非零退出。
- Electron `webview`/`WebContentsView` 可能是独立渲染目标；renderer 截图出现黑块时，改用 guest DOM/CDP 或系统截图，不把黑图当成功证据。
- 用修改前相同 fixture 复测，并检查一个邻近不回归路径。

### 用户验收

- 给用户一个可点击的 fixture 和 1–3 步操作，不让用户重新构造条件。
- 说明成功与失败分别长什么样。
- 用户口头确认后，把它记录为人工验收，不替代自动测试。

## 7. Review 与 PR

创建 PR 前：

- 先把人工验收 fixture 和明确的成功标准交给用户；用户确认目标场景正常后，再等待“提 PR”授权。
- 检查最终 diff、工作树、提交范围和最新 `origin/main`。
- 需要时做一次独立代码审查，修完 Critical/Important 问题。
- rebase 后重新运行受影响的关键测试。
- 使用 `codex/` 分支和带 scope 的 Conventional Commit/PR 标题。
- PR body 包含：用户问题、修复边界、验证命令、真实运行时结果和 `Fixes #<issue>`。
- PR 创建后区分本地通过、CI queued/passed、review approved、merged 和 released；不要提前宣称“已发布”。

## 8. Retrospective：让方法迭代

完成后回答：

1. 哪条证据真正把推断升级为确认？
2. 哪一步本应更早做，能减少多少无关调查？
3. 自动验证是否真的断言，还是只打印/截图？
4. 哪些失败来自产品，哪些来自测试 harness？
5. 新经验是跨 Issue 规则，还是一次性案例细节？

只有用户明确要求吸收时才更新 `lessons.md`。更新时合并近义规则、标出来源 Issue/PR，并运行 Skill 校验。

## 停止条件

- Issue 不属于 `marswaveai/cola`。
- 缺少决定修复方向的用户选择，且不同选择会产生不同产品行为。
- 根因仍 Unconfirmed，继续写代码只能碰运气。
- 需要新的外部权限、生产变更、付费操作或越过用户授权边界。
- 工作树冲突无法安全隔离。

停止时给出已验证事实、具体阻塞和下一项最有信息量的动作。
