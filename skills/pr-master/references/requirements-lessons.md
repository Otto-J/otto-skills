# 需求澄清与表达经验清单

这份文档用于让下一次需求在一至两轮交流内达到可执行、可验收的程度。它记录表达与澄清的经验，不记录完整对话、项目进度或代码改动流水。产品需求文档针对每次任务生成；这份经验清单跨任务复用。

## 需求开始时怎么使用

- 第一轮：读用户原话，区分观察、原因猜测、目标和候选方案；从下方清单挑选与本次有关的条目。先复述已经明确的内容，再集中问最多三个会改变行为、范围或验收的关键问题。
- 追问时给出正常用户场景和推荐选项，例如“正常完成后等待正文显示完；主动停止则立即开始收起，已有内容保留，是否这样？”不要让用户先学会组件、状态字段或 token 才能回答。
- 第二轮：吸收用户回答，直接生成下述列表式需求文档，保留重要问答及决策依据。低风险细节使用明确标注的默认值，已经回答的问题不重复询问；旧假设被推翻时明确作废。
- 两轮是澄清目标，不是硬性上限。确有影响产品语义的未决问题时，只补问阻塞项；不要为凑齐轮数假装需求完整，也不要把全部工程边界变成用户问卷。
- 后续发现新问题，先判断它是遗漏的产品选择还是实现遗漏。只有产品选择需要用户重新决定；既定验收下的实现修复不应伪装成新需求。已有明确 review 范围确认规则仍然适用。

## 第二轮输出的需求文档

使用 list item，按复杂度合并条目，不机械填写空标题：

- 用户故事与目标：谁在什么场景做什么，希望得到什么可观察结果。
- 现象与证据：已经看见的问题；原因猜测另行标注，不当作确定事实。
- 本次范围与对象：改变哪个界面、哪类内容或操作；把“这个”“恢复以前”等指代写成明确对象和行为。
- 行为规则：按实际需要区分进入、更新、正常完成、主动取消等场景，写清触发时机、变化方式与结果。
- 保留约束与非目标：已有内容、原有时机和用户能力中哪些必须保留，哪些相邻行为本轮不处理。
- 验收 QA：用“给定场景 → 用户操作 → 可观察结果”列出主路径与少量关键边界；工程检查由助手补充，不要求用户指定测试实现。
- 澄清问答与决策：仅保留改变了范围或行为的重要 Q/A；标注已确认、暂定假设和确实待确认的内容。
- 改动面与证据缺口：涉及的层级、必要代码和测试的大致规模；区分本地验证、合并、发布与实际环境验收。超过约定规模时及时说明。

## 已吸收的经验

- **R01 · 体验形容词需要拆成可选择的维度。** “太快”“没有呼吸感”是有效的观察，但还不能决定改首次反馈时间、文字呈现节奏还是布局变化。助手先判断和展示主要候选原因，再问“是出现得突兀，还是新增内容把下方顶了一下，或两者都有？”确认后写成可观察结果。不要要求用户拍定毫秒数，也不要直接用固定延迟代替需求澄清。只有节奏需要比较时才给小演示。
- **R02 · “改回来”要说明恢复什么、保留什么。** 历史版本可能同时改变了时机、内容和动画，恢复动效不自动等于完整回退。助手应问“恢复缓动，但保留现在的隐藏时机，对吗？”文档分别记录恢复项和保留项；验收两者同时成立。追溯提交用于确认原有意图，不推断提交人的动机。
- **R03 · “结束／消失”需要核对结束原因和内容去向。** 初始描述通常只覆盖正常完成，容易遗漏主动停止。若产品存在可见停止操作，助手应主动确认：停止是否立即触发收起、是否仍有缓动、已有正文和过程记录是否保留。确认后分别列正常完成与主动停止 QA。错误、切换页面等仅在本次功能相关且可能改变行为时补问，不默认扩大支持范围。界面停止显示运行状态与服务端真正终止应分开表述和验证。
- **R04 · 内容静态与布局平滑可以同时成立。** “碎碎念保持静态”可能指不逐字输出、不闪烁；不表示它占用的空间必须瞬间增加。助手应先复述“文字保持静态，新增和移除时空间平滑变化”的理解，有歧义才追问。需求文档区分内容表现和布局表现，避免恢复一种体验时破坏另一种。
- **R05 · 用户已说清连续性时，助手要负责完整验收。** 用户已经提出“避免高度跳动”，却只验证目标组件最终高度归零，是助手的验证遗漏，不是用户表达不足。无需要求用户补充虚拟列表或操作栏知识。助手应从该目标推导 QA：观察整个内容区域、相邻正文与滚动位置，覆盖过渡过程、动画结束和正式内容接管后一帧；正常完成与已确认的停止场景都要检查。
- **R06 · Review 反馈要分类，不能都归为需求漏项。** “停止后还显示旧进度”对应正常产品路径，可反查是否遗漏停止边界或实现违背既定约束；“参数未进入公共预设”属于工程规范。助手负责提前检查规范，并用“把参数定义集中管理，数值和效果不变”解释 token／preset，不要求用户在第一轮指定文件或抽象。评估竞态时，先核对真实 UI 的弹窗、禁用范围、保存完成时机和发送入口；手工替换组件状态或延迟返回只证明条件下的代码现象，不能直接证明正常用户能稳定触发，更不能照搬严重级别。界面禁用也不能反向证明跨进程操作具备原子性。分别记录技术是否成立、用户触发证据、影响与范围成本；只有未决产品取舍才补问，例如“这个低频窗口是否接受，还是值得增加协调机制？”用户明确接受后，记录为已知边界；已关闭讨论不等于缺陷已修复。若建议改变不同动画的节奏或扩大行为，再交由用户决定。
- **R07 · 默认值与对象独立性要写清生效时机。** 当需求包含“默认设置”“各自独立”“只在新建时生效”时，助手应按创建、草稿编辑、开始执行、后续重开逐项复述状态归属。用户已经明确只初始化新对象时，不再追问是否联动已有对象；仅对确实未定的草稿跟随、旧记录缺少选择等行为补问。可写为“创建时复制默认选择一次；用户可以在对象内主动修改；以后全局默认变化不改写该对象；只有自身选择失效才要求重选”。QA 至少包含两个选择不同的对象、修改或下线全局默认、下线其中一个对象自己的选择、重新打开后再次使用。界面展示、保存记录和实际执行是否一致由助手验证，不要求用户指定实现层。
- **R08 · 暂未就绪与确定不可用要分别决定提交行为。** 当依赖目录、配置或权限信息异步加载时，“禁止使用不可用配置”没有自动回答加载期间是否允许提交。助手应先复述已定行为；若仍未定，用用户操作补问，例如“信息尚未加载完时先阻止发送，加载完成后恢复，是否这样？”需求分别记录未选择、加载中、已失效时是否允许提交、如何恢复和显示什么提示。后端能够等待不等于产品必须放行，前端禁止提交也不自动证明提示内容合适。QA 覆盖在加载完成前后发送，以及确实失效时重新选择；已确认的阻止策略不能被 review 中的技术建议悄悄替换。
- **R09 · 内部优化要区分必要改动和候选机制。** “UI 不变”“考虑事件总线”“便于加日志”分别是体验约束、候选方案和扩展目标，不共同构成使用某种架构的要求。助手应在实施前按“选择 → 保存 → 实际执行”的数据流解释哪些跨层修改是实现既定行为所必需，哪些是抽象、缓存或同步策略的取舍，并检查仓库职责边界；不能让用户看到 PR 后才追问为什么改了运行时。若扩展目标已明确，可采用最小的集中调用或生命周期回调；只有真实订阅者和传播需求未定时才补问。需求写明 UI 保持、执行结果与对象选择一致、诊断逻辑不影响操作结果；缓存删除等可选调整单列理由与成本，不把“读到新选择”扩大为无条件重构或零回归承诺。

## 结束时怎么复盘并更新

- 当用户在本工作流中说“有什么需要总结的”“更新需求经验”等，视为请求更新本清单；若明确说“先讨论／不要写入”，则只输出建议。普通需求讨论不自动写入经验。
- 对照最初输入、助手追问与返回、后续反复澄清、最终验收和已核实的 review。针对每个候选条目回答：最初哪里含糊或缺边界？用户何时补充？助手本可以在第一轮问什么？第二轮应如何写成需求与 QA？不能仅用最终实现反推用户最初就应该知道的细节。
- 给用户的复盘使用列表，每条包含：原表达或概述 → 不清楚／遗漏之处及责任归属 → 建议补问 → 更清楚的需求写法或 QA。每次挑少量高价值条目；交付事实只作必要证据，不套用以 PR 完成情况为中心的总结。
- 只有存在可复用的追问、边界选择或验收改进，才新增经验。先检查 R01–R06 及后续条目，优先补充、纠正或合并原条目；没有新增经验就直说，不为每个 PR 强行新增。
- 后续经验积累只修改这一个文件；不改 SKILL.md、不追加旧案例文件、不复制到记忆库。只有用户另行要求改变 skill 工作流时才调整入口。技能仓库的同步、提交和推送遵守已有授权，文档更新不自动授权外部操作。
- 每个条目保留稳定编号和具体适用条件。存储概括后的经验，不保存完整原始对话、账号、个人身份、私有路径、凭据、临时命令输出或专属项目标识。示例用匿名、可独立理解的场景。
